# Формат выгрузки — техническое описание

Результат экспорта — ZIP-архив:

```
export.xml       — основной файл с данными
files/            — файлы (только если включена опция «Выгружать файлы»)
  <FILE_ID>_<исходное_имя>
```

Импорт распаковывает из архива только `export.xml` и файлы `files/<имя>` (имя — символы `A-Z a-z 0-9 . _ -`, без подкаталогов); всё остальное пропускается (см. `docs/import-format.md`, «Безопасность»).

## Корневой элемент

```xml
<?xml version="1.0" encoding="UTF-8"?>
<export version="2" date="2026-09-18T12:00:00+00:00" mode="element|section_single|section_tree" iblock_id="12">
  ...
</export>
```

- `version` — версия формата (`Export\ExportStep::FORMAT_VERSION`). `2` — с версии модуля 1.1.0, `3` — с 1.2.0 (SEO-шаблоны, блок `<seo>`). В архивах до 1.1.0 атрибута нет; их отличия — в разделе «Архивы версии 1», архивов версии 2 — в разделе «Архивы версии 2».
- `mode="element"` — экспорт одного элемента (FR-1). Внутри `<export>` находится ровно один `<element>`.
- `mode="section_single"` — экспорт одного раздела без вложенных (FR-2). Внутри `<export>` — один `<section>`.
- `mode="section_tree"` — экспорт раздела со всей вложенной структурой (FR-3). Внутри `<export>` — один корневой `<section>`, рекурсивно содержащий дочерние `<section>` в `<sections>`.

Все значения пишутся как есть — без HTML-экранирования, которое делает `GetNext()`: данные читаются через `Fetch()`, а в XML экранируются один раз (текст — `htmlspecialchars`, тексты анонса/детальный/описание — в CDATA).

## `<section>`

```xml
<section id="45" code="news" xml_id="45" active="Y" sort="100">
  <name>Новости</name>
  <description type="html"><![CDATA[...]]></description>
  <picture file_ref="files/301_cover.jpg" name="cover.jpg" size="12345" mime="image/jpeg" description="Обложка"/>
  <properties>
    <property code="UF_SEO_TITLE" type="string">...</property>
    <property code="UF_PUBLISHED" type="date">2026-09-18</property>
    <property code="UF_TAGS" type="string" multiple="true"><value>...</value><value>...</value></property>
  </properties>
  <seo>
    <template code="SECTION_META_TITLE">{=this.Name} — каталог</template>
    <template code="ELEMENT_META_KEYWORDS">ключевые слова для элементов раздела</template>
  </seo>

  <!-- <properties> — пользовательские поля раздела (UF_*): значение одиночного поля — текст узла, множественного — <value>
       на каждое; type — тип поля. Выгружаются только поля с самодостаточным значением: string, integer, double, boolean,
       date, datetime, url; даты — в ISO 8601. У файла, списка и привязки к элементу/разделу значение — ID записи этой
       инсталляции, поэтому такие поля не выгружаются (в журнал выгрузки пишется предупреждение). -->

  <!-- только в mode=section_tree: реальные дочерние разделы, рекурсивно -->
  <sections>
    <section id="46" code="news-2026" active="Y">...</section>
  </sections>

  <!-- только в mode=section_single: перечень прямых подразделов БЕЗ их содержимого -->
  <subsections note="not_included_see_mode">
    <section id="46" code="news-2026" active="Y"/>
  </subsections>

  <elements>
    <element>...</element>
  </elements>
</section>
```

`<sections>` (полные вложенные разделы) и `<subsections>` (только перечень ID/кодов) — два разных, взаимоисключающих тега, зависящие от `mode` в корне документа. Раздел без подразделов не содержит ни того, ни другого. `type` у `<description>` — `html` или `text`.

## `<element>`

```xml
<element id="501" code="news-item" xml_id="501" active="Y" sort="500" main_section="Y">
  <name>Заголовок новости</name>
  <preview_text type="text"><![CDATA[...]]></preview_text>
  <detail_text type="html"><![CDATA[...]]></detail_text>
  <date_active_from>2026-09-18T10:00:00</date_active_from>
  <date_active_to/>
  <preview_picture file_ref="files/502_preview.jpg" name="preview.jpg" size="1111" mime="image/jpeg" description="alt-текст"/>
  <detail_picture .../>

  <!-- только при экспорте отдельного элемента (mode=element): все разделы, к которым он привязан; main="Y" — основной -->
  <sections>
    <section id="45" code="news" path="Каталог &gt; Новости" main="Y"/>
  </sections>

  <properties>
    <property code="AUTHOR" type="S">Иванов И.И.</property>
    <property code="TAGS" type="S" multiple="true">
      <value>тег1</value>
      <value description="описание значения">тег2</value>
    </property>
    <property code="EXPERT" type="E" ref_code="ivanov" ref_xml_id="77">77</property>
    <property code="GALLERY" type="F" multiple="true">
      <file file_ref="files/510_img1.jpg" name="img1.jpg" size="222" mime="image/jpeg" description="Подпись"/>
    </property>
    <property code="EMPTY_PROP" type="S"/>
  </properties>
  <seo>
    <template code="ELEMENT_META_TITLE">Купить {=this.Name}</template>
    <template code="ELEMENT_PAGE_TITLE">{=this.Name}</template>
  </seo>
</element>
```

- Даты (`date_active_from`, `date_active_to`) — в ISO 8601: `ГГГГ-ММ-ДД` либо `ГГГГ-ММ-ДДTчч:мм:сс` («настенное» время сайта, без часового пояса), чтобы архив разбирался на сайте с другим форматом даты. Пустая дата — пустой тег.
- `main_section` — только в режимах раздела. Элемент выгружается под **каждым** разделом дерева, к которому привязан (основной или дополнительной привязкой, таблица `b_iblock_section_element`); `Y` — это его основной раздел (`IBLOCK_SECTION_ID`), `N` — дополнительный.

Внутри `<sections>` элемента, привязанного к разделу через `mode=section_single|section_tree`, этот блок не пишется — принадлежность к обходимому дереву и так очевидна из положения `<element>` внутри `<section>`. Блок `<sections>` элемента пишется только при экспорте одиночного элемента (`mode=element`), где нужно явно перечислить все его разделы (FR-1: «привязку к разделу(ам) — идентификаторы и пути»).

## Файлы (`file_ref`)

- Если «Выгружать файлы» включена: `file_ref` указывает на файл внутри архива (`files/<ID>_<имя>`), плюс атрибуты `name`/`size`/`mime`.
- Если выключена: атрибут `file_ref` отсутствует, но `name`/`size`/`mime` сохраняются — раздел 6 ТЗ.
- `description` — описание файла (для значения файлового свойства — описание значения, если оно задано, иначе описание самого файла).
- Если файл был указан, но не найден на диске: `missing="Y" file_id="..."`, факт фиксируется как предупреждение в журнале задания, выгрузка не прерывается (раздел 9 ТЗ).

## Пустые значения

Поля с пустым значением выводятся как пустой (самозакрывающийся) тег, а не опускаются полностью:

```xml
<description/>
```

Импорт понимает это как «в источнике пусто»: при обновлении существующего элемента пустые свойства и даты активности очищаются (см. `docs/import-format.md`).

## Свойства элементов

Каждое свойство инфоблока — один `<property code="..." type="...">`:

- Непустое одиночное (не файл) — текстовое содержимое тега.
- Множественное (`multiple="true"`) или файловое — вложенные `<value>` (для типов кроме файла) или `<file>` (для типа `F`).
- Тип "Список" (`L`) — выводится отображаемое значение (`VALUE_ENUM`), а не внутренний ID варианта.
- Привязки к элементу (`E`) и к разделу (`G`) — текст значения — ID связанной записи в исходной инсталляции (только для справки), а для сопоставления на другой инсталляции — атрибуты `ref_code` и `ref_xml_id` (её символьный код и XML_ID). Если связанная запись не найдена при выгрузке, атрибутов нет и в журнал выгрузки пишется предупреждение.
- `description` — описание значения (у свойств с включёнными описаниями), на `<property>` для одиночного значения или на `<value>`/`<file>`.
- Пустое свойство — самозакрывающийся `<property .../>`.

## SEO-шаблоны (`<seo>`)

Вкладка «SEO» формы элемента/раздела: мета-теги (`*_META_TITLE`, `*_META_KEYWORDS`, `*_META_DESCRIPTION`), заголовок страницы (`*_PAGE_TITLE`), alt/title/имя файла картинок (`*_PICTURE_FILE_ALT|TITLE|NAME`). Хранятся в `b_iblock_iproperty` (`\Bitrix\Iblock\InheritedPropertyTable`), код — атрибут `code`, шаблон — текст `<template>` как есть (с макросами `{=this.Name}`, `{=this.property.CODE}` и т.п. — они ссылаются на поля и коды свойств, а не на ID, поэтому переносимы). См. `lib/SeoTemplates.php`.

- Выгружаются только **собственные** шаблоны записи (то, что на вкладке «SEO» задано у неё самой, без галки «наследовать»). Унаследованные от инфоблока или раздела-родителя не пишутся: на приёмнике они вычисляются из его собственных настроек. Шаблоны уровня инфоблока («Настройки инфоблока → SEO») не переносятся — это настройки инфоблока, а не записи.
- У раздела собственные шаблоны — это и `SECTION_*`, и `ELEMENT_*` (шаблоны для элементов этого раздела); у элемента — только `ELEMENT_*`.
- Блок пишется всегда, и пустым (`<seo/>`), если своих шаблонов у записи нет: так импорт отличает «в источнике своих шаблонов нет» от архива, выгруженного до 1.2.0.

## Архивы версии 2 (модуль 1.1.x)

То же, что версия 3, но без блока `<seo>`: SEO-шаблоны записей не выгружались. Импорт таких архивов SEO-шаблоны записей приёмника не меняет, страница импорта сообщает об этом.

## Архивы версии 1 (модуль до 1.1.0)

В корне нет `version`. Названия, коды и описания в них прошли через `GetNext()` (HTML-сущности вместо кавычек и `&`, у текстов типа text — `<br />`), даты — в формате сайта-источника, у свойств-привязок нет `ref_code`/`ref_xml_id`, нет `main_section` (элементы выгружались только под основным разделом, а элементы, у которых раздел дерева только дополнительный, не выгружались вовсе), нет типа описания раздела, описаний значений и SEO-шаблонов. Импорт такие архивы принимает, но страница импорта предупреждает: данные лучше выгрузить заново.

## Почему не `\XMLWriter`

Большие деревья разделов (раздел 8 ТЗ: возможна большая глубина и десятки тысяч элементов) экспортируются не за один HTTP-запрос, а серией ограниченных по времени «тиков» (см. `lib/Export/SectionTreeWalker.php`). Между тиками процесс PHP завершается, поэтому состояние обхода должно быть восстановимо из данных, а не из памяти. `\XMLWriter` не поддерживает сериализацию/восстановление внутреннего состояния между запросами, поэтому запись ведётся вручную построчным дозаписыванием (`fwrite` в режиме `a`) уже экранированных фрагментов, а точка возобновления (текущий путь в дереве, смещения постраничной выборки элементов и подразделов, текущая страница ещё не пройденных дочерних разделов) сохраняется в поле `STATE_JSON` таблицы `vspace_ibexport_job` как явный стек кадров обхода в глубину (DFS). И элементы, и подразделы раздела читаются страницами по «Размеру страницы выборки», поэтому число подразделов не ограничено, а в `STATE_JSON` лежит только одна страница. Подробности — комментарии в `lib/Export/SectionTreeWalker.php`.

## Идемпотентность

Повторный запуск экспорта одной и той же сущности с одинаковыми параметрами даёт структурно идентичный `export.xml` (тот же набор узлов, свойств и ссылок на файлы) при неизменных исходных данных — единственное отличие между запусками, помимо самих данных, это атрибут `date` в корневом `<export>` и конкретные имена файлов в архиве (раздел 11 ТЗ, «Идемпотентность»).
