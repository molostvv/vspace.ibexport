# Импорт — правила и ограничения

Импорт читает ZIP-архив в том же формате, что выгружает этот модуль (см. `docs/xml-format.md`), и создаёт/обновляет элементы и разделы в выбранном пользователем инфоблоке. Целевой инфоблок не обязан совпадать с исходным (`iblock_id` в `export.xml` используется только для справки).

## Безопасность архива

Архив приходит от пользователя (или с Яндекс.Диска), поэтому ему не доверяют:

- Из ZIP распаковываются только `export.xml` и файлы `files/<имя>` (имя из символов `A-Z a-z 0-9 . _ -`, без подкаталогов, не начинается с точки) — `lib/Import/ArchiveFileRef.php`. Остальные записи (скрипты, HTML, вложенные каталоги) на диск не попадают; их число показывается на странице импорта.
- Ссылка на файл в `export.xml` (`file_ref`) принимается только в том же виде `files/<имя>`. Ссылка вида `../../bitrix/.settings.php`, абсолютный путь и т.п. отклоняется с предупреждением — иначе поддельный `export.xml` мог бы прикрепить к элементу любой файл сервера.
- Распакованный архив лежит в рабочем каталоге задания со случайным именем (`lib/TmpStorage.php`, см. `docs/admin-guide.md`, «Временные файлы»), закрытом от прямого доступа из веба.
- Каждый шаг страницы импорта (проверка архива, пересчёт, список и загрузка файла с Диска, запуск) принимается только с действующим `sessid` — из формы самой страницы.

## Сопоставление при повторном импорте

Совпадение ищется **по символьному коду** (`CODE`) в целевом инфоблоке:

- Код есть и найдено совпадение, включена опция «Обновлять существующие по коду» — запись **обновляется** (`Update()`).
- Код есть и найдено совпадение, опция выключена — запись **не трогается совсем** (ни поля, ни свойства, ни привязки к разделам), но её ID всё равно используется для привязки дочерних элементов/разделов при обходе дерева.
- Кода нет или совпадение не найдено — создаётся **новая** запись (`Add()`).
- `Update()` вернул ошибку — запись считается **пропущенной**, причина — в предупреждениях задания (свойства такой записи не пишутся).

Идентификаторы (`ID`) из исходного XML не используются для сопоставления — только код.

Каждое обработанное вхождение записи попадает ровно в один счётчик задания: создано, обновлено или пропущено.

### Предпросмотр

После "Проверить архив" страница импорта показывает таблицу записей архива с найденными совпадениями и ожидаемым действием (`lib/Import/ImportPreview.php`, вывод — штатный `CAdminList`). Предпросмотр только читает целевой инфоблок и использует тот же выбор ключа сопоставления, что и импорт (`AbstractNodeImporter::matchFilter()`). Список усечён до 200 записей: на каждую выполняется запрос в БД. Кнопка «Пересчитать» (`STEP=recalc`) заново строит таблицу по текущим отметкам формы и выбранному инфоблоку для уже принятого архива (`Importer::reopen()`), без повторной загрузки файла.

Для совпадений по XML_ID таблица показывает найденную запись (ссылка на её страницу редактирования, `CIBlock::GetAdmin*EditLink`) и предупреждения, а над таблицей — число подозрительных строк:

- **название отличается** — у найденной записи другое название, чем в архиве (без учёта регистра и лишних пробелов). Это предупреждение, а не запрет: запись могли переименовать. Импорт такую запись обновит.
- **несколько записей с таким XML_ID** — совпадение неоднозначно. Импорт такую запись **пропускает** (считается в «пропущено», причина — в предупреждениях задания): обновить «какую-то из» записей нельзя, а создавать ещё одну с тем же XML_ID значило бы плодить неоднозначность. Для раздела сам раздел не обновляется, а вложенные записи помещаются в раздел с наименьшим ID.

Оба признака — только для сопоставления по XML_ID; совпадения по `CODE` работают как раньше.

Над таблицей показана сводка: свойства элементов и `UF_*`-поля разделов из архива, которых нет в целевом инфоблоке (с числом затронутых записей) — их значения импорт пропустит. В самой таблице для строки указано, чего именно ей не хватает («нет в инфоблоке: …»). Для архива версии модуля до 1.1.0 над таблицей выводится предупреждение (см. `docs/xml-format.md`, «Архивы версии 1»).

### Запасной ключ: XML_ID

Если у записи в архиве нет символьного кода, сопоставить её не с чем — она создаётся заново при каждом импорте. Для таких записей в форме импорта есть отдельная опция «Сопоставлять по XML_ID, если нет символьного кода» (по умолчанию **выключена**, выбирается вручную на каждый импорт; хранится в поле `MATCH_BY_XML_ID` задания):

- Работает только для записей **без** кода: если код есть, сопоставление идёт по нему, как раньше.
- Ищется запись (элемент или раздел) с тем же `XML_ID` в целевом инфоблоке; найдена — обновляется/пропускается по той же опции «Обновлять существующие…», не найдена — создаётся новая, и ей **задаётся этот же `XML_ID`** (иначе повторный импорт снова не нашёл бы её).
- Атрибут `xml_id` пишет экспорт (`<section>` и `<element>`); в архивах, выгруженных до его появления, атрибута нет — для них опция ничего не сопоставит.
- Осторожно: Bitrix при создании записи без `XML_ID` подставляет в него её `ID`. Если целевой инфоблок содержит **другую** запись с таким же автоматическим `XML_ID`, она будет принята за совпадение. Поэтому опция включается осознанно — для повторных переносов между одними и теми же инфоблоками.
- Та же опция действует на поиск связанных записей свойств-привязок без кода (см. «Свойства»).

## Разделы и привязки к ним

- Режимы `section_single`/`section_tree`: структура в XML полная, недостающие в целевом инфоблоке разделы создаются автоматически по ходу обхода дерева, с привязкой к разделу-родителю, указанному в форме импорта (пусто — корень инфоблока).
- Привязки элемента к разделам импорт **только добавляет**: существующие привязки (в том числе к разделам вне архива) не снимаются. Элемент, привязанный к нескольким разделам дерева, есть в архиве под каждым из них (`main_section`); основным разделом становится тот, что основной в источнике.
- Такой элемент создаётся или обновляется при первом вхождении, а следующие вхождения только добавляют свою привязку: созданный элемент помечается в штатном служебном поле `TMP_ID` (`vibx<ID задания>_<ID в архиве>`), поэтому находится и без символьного кода. В предпросмотре такие строки помечены действием «Добавить привязку к разделу». Уже существовавший элемент при включённом обновлении обновляется при каждом вхождении.
- Режим `element`: у элемента только плоский список привязанных разделов (`id`/`code`/`path`, где `path` — исключительно текст для человека; `main="Y"` — основной). Если такой раздел не находится по коду в целевом инфоблоке — привязка пропускается с предупреждением; создавать раздел с неизвестным местом в дереве модуль не может.
- Поле «Родительский раздел» в форме импорта не используется в режиме `element`.
- Тип описания раздела (`html`/`text`) переносится; в архивах до 1.1.0 его нет — новый раздел получит `text`.

## Поля элемента

- Название, тексты анонса и детальный (с типом `html`/`text`), активность, сортировка, код — как в архиве.
- Даты активности в архиве — в ISO 8601 и переводятся в формат сайта-приёмника; в архивах до 1.1.0 — в формате сайта-источника и передаются как есть. Пустая дата в архиве при **обновлении** снимает дату и у существующего элемента.

## Свойства

- Определение свойства (по `CODE`) должно **уже существовать** в целевом инфоблоке — импорт не создаёт новые свойства. Свойство с кодом, которого нет в целевом инфоблоке, пропускается целиком с предупреждением.
- Тип «Список» (`L`): значение из XML — это отображаемый текст варианта, а не его ID. Импорт ищет вариант с таким же текстом среди уже существующих значений свойства в целевом инфоблоке. Не найдено — значение пропускается с предупреждением; сами варианты списка модуль не создаёт.
- Тип «Файл» (`F`): файл копируется из распакованного архива через `CFile::MakeFileArray()`. Если `file_ref` в XML отсутствует (выгрузка была без файлов), ссылка недопустима или файл не найден в архиве — значение пропускается.
- Привязки к элементу (`E`) и разделу (`G`): ID из архива **не переносится** — на другой инсталляции он указал бы на чужую запись. Связанная запись ищется в инфоблоке привязки **целевого** свойства (`LINK_IBLOCK_ID`) по символьному коду (`ref_code`), а без кода — по XML_ID (`ref_xml_id`), если включено «Сопоставлять по XML_ID». Не найдена, неоднозначна, у свойства не задан инфоблок привязки или архив прежнего формата (ключей нет) — значение пропускается с предупреждением. Связанные записи должны существовать в целевой инсталляции до импорта (если связанный элемент есть в этом же архиве дальше по обходу, запустите импорт повторно).
- Описания значений (`description`) передаются, если у целевого свойства включены описания.
- Пустое свойство в архиве (`<property .../>`) при **обновлении** элемента очищает значение (у файлового свойства удаляются файлы). Не очищаются значения, которые просто не удалось перенести (не найден вариант списка или связанная запись, файлы не выгружались).
- Остальные типы — значение переносится как текст без изменений.

## Пользовательские поля разделов (`UF_*`)

- Поле должно **уже существовать** в целевом инфоблоке (по коду `UF_*`) — импорт его не создаёт. Поле, которого нет, пропускается с предупреждением «Поле раздела "UF_…" не найдено в целевом инфоблоке, значение пропущено» (без этого Bitrix проигнорировал бы его молча).
- Значение одиночного поля — текст узла `<property>`, множественного — `<value>` на каждое. Даты (`type="date"`/`"datetime"`) — в ISO 8601, передаются в поле объектами `Date`/`DateTime`.
- Типы, значение которых привязано к исходной инсталляции (файл, список, привязка к элементу/разделу), экспорт не выгружает — см. `docs/xml-format.md`.
- Архивы, выгруженные до версии, в которой экспорт начал отдавать `UF_*`, полей разделов не содержат: они просто не переносятся.

## Файлы

- Картинки раздела/элемента (`PICTURE`, `PREVIEW_PICTURE`, `DETAIL_PICTURE`) переносятся напрямую (с описанием файла), если в XML есть допустимый `file_ref` и файл физически присутствует в архиве. Если файлов нет (выгрузка была без опции «Выгружать файлы», файла не было на диске при экспорте или у источника картинки нет) — поле не трогается (не затирается пустым значением).

## Что модуль не делает

- Не создаёт определения свойств инфоблока и варианты списков — они должны существовать в целевом инфоблоке заранее.
- Не переносит права доступа, торговые предложения, привязки к пользователям и что-либо, не входящее в `docs/xml-format.md`. Связи между инфоблоками переносятся только через свойства-привязки `E`/`G` (по коду/XML_ID связанной записи).
- Не удаляет ничего в целевом инфоблоке — импорт только создаёт и обновляет (привязки к разделам только добавляются). Исключение — значения свойств и даты, пустые в архиве, при обновлении элемента.

## Возобновление и большие деревья

Как и экспорт, импорт режимов `section_single`/`section_tree` выполняется тиками, ограниченными по времени (`Options::getTickBudgetSeconds()`), с возобновлением между тиками. Курсор обхода — путь индексов от корня по уже распакованному `export.xml` — хранится в `STATE_JSON` записи `vspace_ibexport_import_job` (см. `lib/Import/SectionTreeWalker.php`).

## Журнал и предупреждения

Каждый запуск импорта — строка в «Журнал импорта»: инфоблок, режим, статус, счётчики создано/обновлено/пропущено. Частичные сбои (свойство/вариант/раздел/связанная запись не найдены, файл отсутствует, недопустимая ссылка на файл) не прерывают импорт — копятся в `WARNINGS_JSON` записи задания, как и в экспорте.

Одинаковые предупреждения объединяются в одно со счётчиком повторов, например «Свойство с кодом "X" не найдено в целевом инфоблоке, значение пропущено. (×170)» — вместо сотни одинаковых строк. Размер списка ограничен (`lib/WarningList.php`: 100 разных сообщений и ~60 КБ, колонка — `TEXT`); то, что не поместилось, учитывается итоговой строкой «… и ещё N предупреждений не показано (лимит журнала)». Раньше без лимита список при переполнении колонки молча терял накопленное.
