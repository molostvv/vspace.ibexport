# Импорт — правила и ограничения

Импорт читает ZIP-архив в том же формате, что выгружает этот модуль (см. `docs/xml-format.md`), и создаёт/обновляет элементы и разделы в выбранном пользователем инфоблоке. Целевой инфоблок не обязан совпадать с исходным (`iblock_id` в `export.xml` используется только для справки).

## Сопоставление при повторном импорте

Совпадение ищется **по символьному коду** (`CODE`) в целевом инфоблоке:

- Код есть и найдено совпадение, включена опция «Обновлять существующие по коду» — запись **обновляется** (`Update()`).
- Код есть и найдено совпадение, опция выключена — запись **не трогается** (остаётся как есть), но её ID всё равно используется для привязки дочерних элементов/разделов при обходе дерева.
- Кода нет или совпадение не найдено — создаётся **новая** запись (`Add()`).

Идентификаторы (`ID`) из исходного XML не используются для сопоставления — только код.

### Предпросмотр

После "Проверить архив" страница импорта показывает таблицу записей архива с найденными совпадениями и ожидаемым действием (`lib/Import/ImportPreview.php`, вывод — штатный `CAdminList`). Предпросмотр только читает целевой инфоблок и использует тот же выбор ключа сопоставления, что и импорт (`AbstractNodeImporter::matchFilter()`). Список усечён до 200 записей: на каждую выполняется запрос в БД.

### Запасной ключ: XML_ID

Если у записи в архиве нет символьного кода, сопоставить её не с чем — она создаётся заново при каждом импорте. Для таких записей в форме импорта есть отдельная опция «Сопоставлять по XML_ID, если нет символьного кода» (по умолчанию **выключена**, выбирается вручную на каждый импорт; хранится в поле `MATCH_BY_XML_ID` задания):

- Работает только для записей **без** кода: если код есть, сопоставление идёт по нему, как раньше.
- Ищется запись (элемент или раздел) с тем же `XML_ID` в целевом инфоблоке; найдена — обновляется/пропускается по той же опции «Обновлять существующие…», не найдена — создаётся новая, и ей **задаётся этот же `XML_ID`** (иначе повторный импорт снова не нашёл бы её).
- Атрибут `xml_id` пишет экспорт (`<section>` и `<element>`); в архивах, выгруженных до его появления, атрибута нет — для них опция ничего не сопоставит.
- Осторожно: Bitrix при создании записи без `XML_ID` подставляет в него её `ID`. Если целевой инфоблок содержит **другую** запись с таким же автоматическим `XML_ID`, она будет принята за совпадение. Поэтому опция включается осознанно — для повторных переносов между одними и теми же инфоблоками.

## Разделы

- Режимы `section_single`/`section_tree`: структура в XML полная, недостающие в целевом инфоблоке разделы создаются автоматически по ходу обхода дерева, с привязкой к разделу-родителю, указанному в форме импорта (пусто — корень инфоблока).
- Режим `element`: у элемента только плоский список привязанных разделов (`id`/`code`/`path`, где `path` — исключительно текст для человека). Если такой раздел не находится по коду в целевом инфоблоке — привязка пропускается с предупреждением; создавать раздел с неизвестным местом в дереве модуль не может.
- Поле «Родительский раздел» в форме импорта не используется в режиме `element`.

## Свойства

- Определение свойства (по `CODE`) должно **уже существовать** в целевом инфоблоке — импорт не создаёт новые свойства. Свойство с кодом, которого нет в целевом инфоблоке, пропускается целиком с предупреждением.
- Тип «Список» (`L`): значение из XML — это отображаемый текст варианта, а не его ID. Импорт ищет вариант с таким же текстом среди уже существующих значений свойства в целевом инфоблоке. Не найдено — значение пропускается с предупреждением; сами варианты списка модуль не создаёт.
- Тип «Файл» (`F`): файл копируется из распакованного архива через `CFile::MakeFileArray()`. Если `file_ref` в XML отсутствует (выгрузка была без файлов) или файл не найден в архиве — значение пропускается.
- Остальные типы — значение переносится как текст без изменений.

## Файлы

- Картинки раздела/элемента (`PICTURE`, `PREVIEW_PICTURE`, `DETAIL_PICTURE`) переносятся напрямую, если в XML есть `file_ref` и файл физически присутствует в архиве. Если файлов нет (выгрузка была без опции «Выгружать файлы» или файла не было на диске при экспорте) — поле не трогается (не затирается пустым значением).

## Что модуль не делает

- Не создаёт определения свойств инфоблока и варианты списков — они должны существовать в целевом инфоблоке заранее.
- Не переносит права доступа, торговые предложения, связи с другими инфоблоками (кроме привязки раздел↔элемент) и что-либо, не входящее в `docs/xml-format.md`.
- Не удаляет ничего в целевом инфоблоке — импорт только создаёт и обновляет.

## Возобновление и большие деревья

Как и экспорт, импорт режимов `section_single`/`section_tree` выполняется тиками, ограниченными по времени (`Options::getTickBudgetSeconds()`), с возобновлением между тиками. Курсор обхода — путь индексов от корня по уже распакованному `export.xml` — хранится в `STATE_JSON` записи `vspace_ibexport_import_job` (см. `lib/Import/SectionTreeWalker.php`).

## Журнал и предупреждения

Каждый запуск импорта — строка в «Журнал импорта»: инфоблок, режим, статус, счётчики создано/обновлено/пропущено. Частичные сбои (свойство/вариант/раздел не найден, файл отсутствует) не прерывают импорт — копятся в `WARNINGS_JSON` записи задания, как и в экспорте.
